## Compatibility and explicit bounds

- Operating v1 is a derived API contract, not a new persisted entity/store. GETs use no-migration validated reads and do not repair, backfill, reconcile, refresh providers or execute actions. Absent optional data differs from malformed/future/unavailable data. Legacy v1 profiles remain unchanged and unavailable to Q until the separate existing migration is explicitly used.
- Source snapshot reads reject redirected/unsafe/oversized files and changing identities; the service's default aggregate byte ceiling is 16 MiB, with tighter underlying store limits retained. Task inventory is capped at 10000 files and 16 MiB combined. Source facts are bounded at 10000 and objective ancestry at eight. Requested `page_size` is 1..50; a response section/page can contain zero to 50 rows. SURTEC uses six visible rows, objective detail eight, readiness six per section, and delivery selection at most 50 same-project issues. Partial coverage cannot claim exact totals; cursors are not signed authority or an immutable cross-store snapshot.
- `delivery_observation` is optional, independently strict v1 inside existing issue evidence; outer issue/evidence contracts retain v1. Old absent facets remain absent. Null/malformed/future values fail closed without fallback, migration or source-byte repair. Observed-at is explicitly entered and cannot exceed server-record time; date-only review values never become invented timestamp observations.
- Manual input is limited to 8 KiB; summary 500 characters, source reference 300 and next action 500. A source reference is safe opaque data/simple HTTP(S), never fetched, executed or treated as a file path. At most 64 manual facts per issue, 500 evidence references per issue, 5000 aggregate evidence records and 20000 audit events are allowed; overflow refuses rather than evicts. Other existing issue bounds remain unchanged.
- Recording rereads under the issue lock and exact expected revision, rejects queued/running task ownership or any owner workflow not completed/cancelled, and appends informational evidence plus metadata-only audit. Optional commitment checks use a stable bounded same-project snapshot, not a cross-store transaction. No scope/lifecycle/task/grant/testing receipt/commitment state is changed. Later approvals need the new issue revision normally.
- The UI starts without implicit delivery reads/writes, requires explicit consultation/selection and unchecked confirmation, invalidates confirmation on changed bindings and uses a submission mutex. Unknown outcomes require explicit reread, not automatic replay. Private text is revealed per record as text only; it does not enter operating summaries, generic task drafts or implicit context.
- P budget production cutover remains `not-enabled`, continuity remains `deferred`. No new admission, scheduler, lifecycle, runtime, retry, Harness apply/repin, deployment, publication, client message or backup/restore effect is enabled by Q.

See [migration compatibility](../architecture/organization-state-migration.md), [local issue authority](local-work-issues.md) and the [threat model](../security/threat-model.md) for underlying contracts. Same-user filesystem mutation, imperfect pattern redaction and separate durable writes remain residual risks, not guarantees strengthened by this read model.
