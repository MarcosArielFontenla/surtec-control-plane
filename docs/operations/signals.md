# Deterministic signal feed

The read-only portfolio feed is `GET /api/signals`. It returns a versioned, bounded list of signals with source, severity, evidence timestamp, observed timestamp, a plain-language reason, a suggested action, an explicit ranking tier/order, and the project's category when a local profile exists (`personal`, `internal-tool`, `surtec-product`, `client-product`, `experiment`, or `template`). Objective signals use `source: objective`; global company-level signals are anchored to the reserved `project_id: surtec`, while relationship signals are anchored to the real project. It does not return the profile's client identifier or name. It uses the existing loopback API protections; the route is marked `Cache-Control: no-store` because it overlays private local operating context.

Signal evidence is assembled server-side from local Git status, the cached aggregate integrations reader, the cached GitHub issue inbox, task snapshots, local portfolio profiles, the local organization/objective store, and local project notes. The consumer makes one feed request rather than one request per project. Integration reads have bounded concurrency and an individual provider/project failure becomes a short warning while other sources continue. Provider errors and response bodies are not copied into signal evidence.

The engine applies these deterministic thresholds: long-running CI is at least 60 minutes; recent high-priority issue activity and recent project activity use 7 days; profile and objective reviews become stale after 30 days; an unresolved note becomes eligible after 14 days; project deadlines approach within 7 days and objective targets within 14 calendar days; both use the machine's local calendar. Objective rules identify active objectives without projects or success criteria, active non-personal projects without objectives, links to paused/cancelled objectives, and achieved objectives with open GitHub inbox issues. Personal projects are exempt from the no-objective rule. Until Phase L adds local issues, the achieved-objective rule is limited to open GitHub inbox evidence. Client profile deadlines and delivery commitments already past due rank ahead of other commitments. Active commitments due within 7 calendar days (including today) produce due-soon signals; blocked commitments produce a blocked signal. Completed and cancelled commitments do not produce signals. Lower numeric profile priority values indicate higher priority.

Commitment evidence includes a bounded title, date, priority, criticality, and state for ranking and review. It does not include the client's name, private notes, issue title, or provider payload. The client status and relationship are read from local state; project associations are derived from the canonical `ProjectProfile.client_id` reference.

`POST /api/signals/:id/action` accepts one of `acknowledge`, `snooze` with a future ISO date/time, `pin-for-today`, `dismiss`, or `resolve`. Every mutation requires the same in-memory session token as other local API writes. Signal evidence is recomputed; only the human interaction record is persisted at `state/signals/human-state.json` (ignored by Git). State writes use a cross-process file lock and unique temporary file followed by atomic replacement. Invalid or unsupported future-version files are never repaired or overwritten automatically.

For signal occurrences whose first interaction is recorded after Phase I, the first action and evidence timestamp are retained for aggregate recommendation outcome and evidence-to-action metrics. Historical first actions are not inferred from older human-state records. See [local feedback metrics](feedback-metrics.md) for denominator rules and privacy boundaries.

Snoozes reopen when their date/time passes without a read-side write. Pins expire at the next local calendar date. Dismissed occurrences are hidden while their evidence remains present. IDs are stable for a project/source/type/occurrence key. CI run IDs, task ID plus attempt, issue number plus update time, note ID, deadline date, deployment timestamp when available, and PR number plus review state/update time can distinguish separate occurrences. For deployment checks without a deployment timestamp or other transition evidence, recurrence may reuse an earlier ID.

Evidence is intentionally limited: no provider payload, issue title/author/URL, note text, deployment URL, task instructions/result text, credential, or absolute repository path is included. Project IDs, bounded branch names, task/issue/note/PR/objective identifiers, objective titles, status enums, counts, labels, and timestamps may be present when they explain a rule. State is local and not encrypted by this application; protect it using host account and disk protections.

The deterministic engine still accepts paused-session evidence, but session recommendations are not currently enabled in the production signal feed. Phase G adds a separate persisted resume card in `Hoy` and project detail; it does not fabricate priority signals from session state. Connecting session evidence to signal ranking can be evaluated separately once real usage demonstrates a useful rule.

Run the deterministic browser/API smoke with `pnpm smoke:signals:playwright`. It launches Chromium against an isolated loopback API server, uses synthetic evidence and temporary state, exercises the session-protected action endpoint, restarts the service, then removes only its uniquely named temporary directory. It does not make provider or paid model calls.
