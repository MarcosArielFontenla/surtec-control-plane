# Phase R · Apply a reviewed personal scaffold

## Scope

The first real-project increment applies `personal@1` to one operator-selected checkout registered in Surtec. It creates only the missing approved templates `.agents/templates/entity.spec.yaml` and `.agents/templates/feature.tasks.md`. An eligible checkout already has a physical `.agents/templates` directory. The observed root primer, differing files, staged or locally deleted tracked paths, and identical preexisting files are preserved. An additions-only operation with nothing to write returns an effect-free result. The project and its exact preview are selected after this implementation is qualified.

Use a dedicated local CLI with `preview`, `apply`, `status` and `rollback`. The project argument is a registered ID. Existing project policy resolves the checkout and its trusted local containment. The CLI accepts the explicit archetype ID. It keeps the project registry, agent sandbox ceilings, command policies, routing, dashboard and existing Doctor profiles intact. The mutation is the operator's narrow authorization for the listed template paths. Generated updates, obsolete files, directory provisioning, project commands, Git writes and automatic rollback are outside this increment.

## Preview and approval

1. Resolve the checkout with `PolicyService.project` and validate the physical root and approved destination parent. Reject redirected paths, ambiguous filesystem identity, links, active Git operations and pending index locks. Use bounded read-only Git arguments with optional locks and FSMonitor disabled. Verify the actual Git top level, bind the checkout and parent directory identity, branch and HEAD, and inspect the selected paths in the index and ignore policy. Exclude absent paths that Git already tracks, stages or ignores, with reasons in the preview. Preserve unrelated local edits.
2. Reuse `previewHarnessScaffold`, `loadHarnessSource` and Doctor. Display the project identity, source version and fingerprint, decisions, exact canonical additions, preserved conflicts, preimage and rollback scope. Bind the apply digest to the original preview fingerprint, current checkout identity and Git evidence, and sorted exact effects. Include only relative paths, bounded facts and canonical bytes in the rendered output.
3. `apply` shows a fresh preview and accepts its exact apply digest at an interactive terminal. Require the operator to confirm exclusive access for the short mutation window, including editors and other Surtec state roots. Acquire the existing maintenance exclusive boundary for the current state root, then reassemble the plan and verify digest equality before creating the operation record or target files. The maintenance boundary coordinates its participants. External writers remain an operator-controlled prerequisite. A stale plan, cancelled prompt or busy boundary yields a refusal without a target write. A preview, stored digest or record alone carries no mutation authority.

## Backup and apply

Create a schema-versioned operation record under ignored `state/harness/scaffold-operations/<operation-id>/`. Limit each operation to two entries, up to 256 KiB of canonical bytes per entry and 64 KiB of JSON metadata. Persist and read back the sealed preimage before the first write to the checkout. The preimage includes exact absence and parent identity for each intended addition, observed hashes and ownership evidence for preserved entries, the approved digest, the prior Doctor fingerprint and Git binding. The two templates have no original bytes when absent. The private operation directory retains the approved canonical bytes and their hashes for verification and recovery. Existing project files are read only as needed for the preview and are represented in the operation by bounded metadata. The reviewed source registry and the existing Harness profiles store keep their current formats.

Record a revisioned intent before each publication. Stage the exact canonical bytes next to the destination using an exclusive, operation-owned name. Flush, validate and record the staged file identity and digest. Publish without replacement using the same-filesystem hard-link pattern already used for routine reports. Recheck the named and opened identities before using any file. Remove the owned stage and verify that the destination now has one link. Filesystems that cannot safely complete this primitive fail closed. Publication is atomic per path. The record distinguishes partial completion across the two paths.

## Verification and ownership

After apply, verify all published files against the approved hashes, their recorded identities and the physical parent. Re-observe preserved paths and applicable Git projections, confirm the index and HEAD were preserved, and run the actual Doctor. Bind the verification receipt to the final observed bytes and operation revision. Report the scoped template verification separately from the Doctor's overall validation status. No project commands or instructions are executed, so overall validation can remain `unknown`. A `legacy` or `warning` Doctor baseline may remain in that state. The operation proves ownership of its exact creations for rollback. An identical preexisting copy keeps its original ownership, and the Doctor still uses its current trusted declarations.

## Recovery and rollback

`status` reads the journal and current evidence without changing either. On interruption, a final path matching the sealed stage or post-write identity can be attributed to that operation. A missing checkpoint, unrecoverable identity, foreign file or malformed/future record produces `needs-review`. Recovery never replays an apply or guesses ownership from a hash. An abandoned or unknown maintenance lock blocks mutations until its ownership is inspected and the lock is resolved separately. This increment adds no age-based release or override.

`rollback` shows a fresh plan for the operation, then requires independent interactive approval of that plan's digest. Under exclusive access, revalidate the sealed preimage, checkout, Git binding and all affected paths before the first removal. Use the operation's sealed bytes even after a later canonical release. Remove only a file proven to have been created by the operation, still matching the saved identity, metadata and hash, with one link, and with current ownership evidence compatible with removal. A tracked, staged, replaced or edited addition blocks the rollback before deletion. An already absent file is reported as such. The original preimage for every allowed write was absence, so the operation never has to restore or delete a preexisting file or directory. A failure after a proven removal leaves a partial result for review. Repeated status and approval flows can distinguish verified absence from a recorded removal. Keep the receipts for audit and treat any unresolved removal as indeterminate.

## Qualification

Qualify the normal CLI service path against isolated Git and state fixtures. Cover both additions and a mixed tree with preserved conflicts, exact no-op, stale approval, guard contention, tracked deletion, links, collision immediately before publish, interruption after publish, repeat requests, failed verification and a successful rollback. Prove that a same-byte replacement and a later indexed or edited addition survive a refused rollback. Inject failures between durable intent, publication, verification and rollback checkpoints. Verify the before and after byte inventories, the Git index and HEAD, the actual Doctor and the cleanup of owned resources. The guarded acceptance catalog runs `pnpm test`, `pnpm schemas:check` and `pnpm typecheck` with the existing ceiling of 900 seconds per command.

The first real checkout is reserved for a separately approved pilot. Present the exact apply preview and exclusion window before writing. Present a separately reviewed rollback plan before removing any actual addition. The focused qualification covers rollback in the disposable fixture, so a successful pilot does not have to remove the delivered templates to prove the mechanism.
