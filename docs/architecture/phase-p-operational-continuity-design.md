## Budget resolution and accounting

Applicable constraints are company, selected objective and its existing validated ancestors, project, issue where present, role and execution, plus current worker/workflow/correction policy. The most restrictive configured remaining hard cap wins for each dimension: runtime, attempts, cumulative tokens, concurrent reads/writes, review attempts/runtime/tokens and automated corrections. Review and correction are independently inspectable labels of canonical charges, not extra copies added to the total.

Attribution is server-owned and frozen: company `surtec`, `issue.objective_id` otherwise the project's primary linked objective, otherwise no objective; maximum ancestry depth remains the current eight. Project/objective links form a graph, not an invented single-parent project tree. Changing links cannot transfer old consumption or charge every secondary link. Personal work without an objective remains supported.

The read model shows cap, consumed, reserved, remaining or unavailable, warning, period, policy IDs/revisions/fingerprints, review/correction breakdown and machine-readable denial. Remaining uses consumed plus outstanding reservations. Period buckets are fixed at admission; active/unknown reservations survive rollover. Unknown interrupted usage is never treated as zero or refunded by restart.

Admission sequence:

1. Preview resolves trusted policy/attribution and existing scope/context without reserving or executing. Balances/receipt histories are not instruction sources or immutable context fingerprints.
2. On exact human confirmation or already-approved bounded workflow stage authority, recompute current availability and atomically reserve every applicable dimension. Reserve the admitted stage/task cap, not both a whole workflow grant and its child stage. Failure of one dimension creates no partial reservation.
3. Persist a deterministic task admission intent and its BudgetAdmission v1 binding. The binding identifies task/project/role/agent, scope and policy versions, period buckets, manifest/cap fingerprint and reservation; for tasks whose context admission is v2, BudgetAdmission v1 additionally binds exact workflow/stage/generation/grant. No BudgetAdmission v2 is proposed. It is not a live controller proof.
4. The existing worker creates run IDs at claim. Before every model/worktree/verification effect, require committed matching intent/reservation, unchanged restrictive policy, private controller/lease ownership and all current scope/context/consent gates. Revalidation may exclude only this task's exact reservation; it cannot increase the admitted cap or lend it to another task.
5. Account attempts/active runtime and normalized cumulative usage once per exact task/run. Duplicate, decreasing or repeated terminal notifications are idempotent monotonic deltas. Task and workflow counters describe the same underlying usage; do not sum them again.
6. Settle only proven usage and unused reservation. Cross-store persistence gaps, missing final receipts, lease loss and ambiguous interruption keep a conservative hold/unknown classification and block affected admission pending evidence, never automatic refund or replay.

Use the current short synchronous locking discipline, but a dedicated budget lock with token/inode ownership and no age stealing, modeled on the workflow store. No await, network/Git effect or nested scheduler/task/issue lock inside its callback. Cross-store operations use durable intents and revision fences; do not claim a multi-file transaction. Test admission/claim/settle crash points and the final unit of capacity contested by two requesters/workers.

Preserve existing per-attempt leaf runtime and cumulative task tokens, while configured parent/workflow runtime is cumulative across runs. Admission reserves the first prospective attempt; each retry needs a fresh exact owned atomic top-up under its unchanged admitted task cap, remaining parent limits and normal retry/controller rules. A held task token allowance survives retry and decreases only by proven consumption; never reserve it twice.

| Dimension | Reservation and consumption |
| --- | --- |
| Attempts/review attempts | Hold one prospective attempt before its claim, charge once at claim, reserve the next only if permitted. The immutable task attempt ceiling is not consumption. |
| Runtime/review runtime | Hold one admitted per-attempt cap, debit proven active run time; a retry reserves another bounded run slice. Cumulative parent/workflow limits reduce the next slice. No implicit cumulative leaf cap is introduced when parent runtime is unconfigured. |
| Task tokens/review tokens | Hold the permitted remaining cumulative token allowance; move monotonic proven deltas from reserved to consumed, keep uncertainty held. Review is a label, not duplicate total usage. |
| Concurrent reads/writes | Hold one applicable execution slot, not the entire configured concurrency cap; release only after proven terminal ownership/effect completion. Pending/unknown ownership is explicit. |
| Corrections | Hold the one existing opted-in lineage allowance before correction admission, consume once; review stages and root accounting remain separately bounded. |

The runtime adapter must preserve absent/incomplete/invalid usage as unknown, including after a previously valid intermediate notification; retain proven monotonic charges without declaring a missing final total complete. Explicit complete zero is distinct from a missing total. Tests cover missing/null/negative/non-finite/fractional, decreasing, duplicate and incomplete terminal receipts. Include a two-attempt regression whose cumulative runtime exceeds the per-attempt cap but fits configured parent caps (or no parent runtime cap).

## Safe routines

The four actions are code allowlisted: `refresh-evidence`, `evaluate-signals`, `propose-issues`, `generate-local-report`. Scope is company/objective/project with validated existing IDs; there is no free-form command, URL, path, model prompt, adapter or executable metadata. Mutating the routine definition requires protected local HTTP/session checks and expected revision; source configuration must be revalidated before each occurrence.

Reuse the existing worker tick with a finite routine hook, not a second timer/service/scheduler. A unique occurrence key binds routine ID, revision and UTC slot; durable admission precedes effects, private ownership precedes execution, and completed slots never run twice. `coalesce` retains at most one pending slot. Restart may perform at most the explicitly configured catch-up; ambiguous occurrence ownership needs review. Disabling or cancellation prevents new effects, without deleting accounting or history. Dispatch one tracked background occurrence after normal task claims without awaiting its completion inside `runOnce` or keeping `ticking` true; own its cancellation/completion in the existing worker lifecycle. Tests prove both heartbeat and new task claims/cancellation progress during a delayed fake adapter.

The ledger supports two explicit subject kinds: task admission/run and routine occurrence/revision/slot. Routines use internal occurrence-owned reservation proofs, never fabricated TaskEnvelopes, agent roles or context admission v2. Apply company/selected objective ancestry/project scope and trusted routine policy as relevant; no issue/agent role is invented. For a multi-project refresh, freeze the bounded selected project IDs and conservatively intersect their applicable read/runtime limits for the whole occurrence. Scope projections overlap and are not summed; do not invent per-project elapsed time or cost. Routine consumption is one known deterministic attempt, measured runtime and one read slot, with exactly zero model calls/tokens and no write execution slot. Unknown resource evidence still blocks the relevant measured dimension.

Actions are deterministic and make no model calls. They may read trusted Git/CI/deployment/dependency/health facts, evaluate existing pure signal rules, flag stale company/objective/project/issue/session/Harness facts, write bounded local receipts/reports or propose a local issue for human review. An occurrence-specific proposal key prevents duplicate issues across restart; it never authorizes the proposal, changes an existing issue/objective, starts workspace-write work or publishes anything.

Read-only does not mean offline: external provider reads require existing explicit trusted integration configuration and URL/argument/environment protections. Missing provider consent/configuration is unavailable evidence, not implicit enablement. Tests use fake providers, a controlled clock and synthetic repositories with network disabled.

Do not call migration-bearing portfolio list reads from routines. Add a validated no-migration reader that preserves v1/v2 bytes or returns a visible migration requirement. Do not reuse list helpers that skip invalid tasks/notes as authoritative facts. Invalid required state blocks that occurrence without making the whole platform unavailable.

Current Git/provider/dependency helpers can block synchronously for 20..60 seconds against a 30-second lease. Routine-specific refresh uses bounded asynchronous subprocess/network paths with existing fixed arguments, reduced environment and trust rules; no install/update command or arbitrary shell. This is not a wholesale endpoint rewrite. A delayed fake adapter must prove concurrent worker heartbeat and cancellation remain effective. Shared TTL/coalescing prevents multiplication of refresh calls per GET/tick.

Receipts contain action/scope/policy/slot IDs, start/end time, freshness/counts, hashes, budget outcome and sanitized failure/next action. They exclude private notes, instructions, raw provider payloads and credentials. The report destination is the code-owned `reports/routines` directory under the operator's explicitly selected canonical local state root; only a safe occurrence ID determines its filename. There is no caller-defined destination, path field in Routine or report-export endpoint. Validate privacy/containment before writing, and report unavailable if that boundary is unsafe. Today presents last/next run, stale/unavailable/partial results and exact failures separately from API/worker health; no optional routine outage is a global outage.
