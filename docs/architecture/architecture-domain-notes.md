# Architecture domain notes

## Phase J organization design boundary
The Phase J design baseline is defined in [ADR-0003](../decisions/ADR-0003-organization-domain-boundary.md), [Issue lifecycle v1](issue-lifecycle-v1.md) and the [migration contract](organization-state-migration.md). Phase K subsequently implemented organization/objective links and the portfolio-profile migration; Phase L adds local issues, authorized scope, task/attempt/session lineage, immutable candidates and evidence-bound local acceptance. The durable task runtime retains its owner and publication gates; local issue acceptance never publishes. See [Local work issues](../runbooks/local-work-issues.md) and [Phase L acceptance](../runbooks/phase-l-acceptance.md) for the current implementation and evidence, rather than interpreting the historical Phase J exclusions as current readiness.
## Phase M Harness observations
`lib/harness` inspects registered local checkouts without executing their instructions or writing their files. The trusted `registry/harness-sources.yml` pins a curated 25-entry H1-H4 manifest; a changed baseline becomes unknown, not automatically adopted. Version detection requires an exact reviewed baseline match; primer/skill versions are not Harness release versions. Protected explicit refresh persists bounded profiles under `state/harness/profiles.json`; GET inventory and Doctor never write observations. Signals consume saved observations, retain their evidence timestamps, and do not authorize repair. Ownership and validation require explicit trusted metadata; script presence and matching hashes are not proof. See [Phase M acceptance](../runbooks/phase-m-acceptance.md) for limits and verification.
## Governed context and Phase O workflows
Six logical Codex profiles intersect existing project/agent permissions; an issue's stored agent assignment remains unchanged. Explicit protected preview exposes attributed source metadata, exclusions and effective requirements, never a rendered private prompt. Application-selected project files are contained and bounded; defaults are 500 physical lines / 60000 UTF-8 bytes, separate from runtime token limits. Client categories start empty. Trusted Harness routes select complete applicable instructions/skills without recursive Markdown inclusion or canonical repinning.
Manifest/testing receipts remain v1; admission explicitly dispatches legacy, v1 analysis/issue or v2 server-owned workflow stages without historical backfill. Preview issuance is bounded, process-local and expires after five minutes; restart requires fresh issuance, not automatic replay. Persisted tasks retain evidence and reassemble current authority independently of that ledger. See [Phase N](phase-n-context-design.md) and [compatibility](organization-state-migration.md#phase-o-additive-workflow-compatibility).
Phase O provides analysis, implementation, quality-review, operations-investigation and trivial-change under exact root/per-role consent and finite aggregate caps. The existing worker runs sequential roles; Reviewer/QA have separate read-only task/thread contracts over the inactive implementer's exact managed candidate, checked before/after. Plan, risk acknowledgement and final criterion acceptance remain human gates. One correction is off by default, consumed before admission, uses the original Engineer/scope and exact prior candidate base, then fresh verification/reviews; replacement/restart cannot refund it. Workflow v1 stores immutable handoffs/receipts, intents, run charges and lineage; recovery reconciles only provable unstarted gaps. See [design](phase-o-workflow-design.md) and [acceptance](../runbooks/phase-o-acceptance.md); neither product role chaining nor development helpers activate Harness multi-agent orchestration.
## Explicit retained Planner proposal recovery

An implementation workflow may explicitly offer its first valid `needs-review` Planner proposal for a separate human exact-plan decision. `planner_recovery` is an optional strict immutable nested v1 receipt in workflow v1; the original task/result/events/output and charged usage remain unchanged. A retained running stage may terminalize as `needs-review`, never fabricated `completed`. The closed protected 4-KiB `/api/workflows/:id/planner-recovery` action requires current source/revision/authority bindings, independently validated complete terminal usage and explicit indexed question/risk acknowledgements. Its derived detail offer is read-only and issues no preview grant; list summaries omit private recovery bodies.

The new human planning basis applies only after its exact plan approval, through the same controller, successor admission, handoff and context guards. It does not change ordinary terminal-success requirements, other roles, unknown accounting, verification, review depth, candidate acceptance or existing unstarted admission reconciliation. The finite workflow can complete with this one human-adopted planning prerequisite while preserving the original incomplete model status. No task, attempt, grant or budget is recreated or refunded. See the [reviewed bounded delta](../proposals/factory-local-f3-planner-recovery-design.md) for eligibility, technical acceptance status and the separately gated real re-entry; implementation descriptions are not passing evidence.

## Explicit first uncharged implementation claim recovery

The optional `uncharged_claim_recovery` v1 facet journals one narrowly qualified first Engineer scheduler claim that failed before controller charging or execution. A closed source/native/archive proof, exact original task/events/intent, one known Planner charge, unchanged approved plan/current context and a stopped idle owning worker are required together. Missing accounting alone cannot prove this boundary. The internal action has no HTTP, CLI or UI entry point and starts no worker.

Prepared receipt, same-task requeue, appended recovery event and ready receipt are separate fenced operations. A partial journal remains blocked and requires the same explicit operation; an unrecorded event gap is not repaired. Immutable provenance retains the original failure and archived bytes, while the current task snapshot advances. Numeric workflow charges/caps and task attempts never decrease; the next normal claim increments the task attempt and charges through the existing controller. Planner bytes/approval remain unchanged. See the [bounded delta](../proposals/factory-local-f3-engineer-claim-recovery-design.md) for technical evidence and the separate live gate.

## Phase Q operating views and delivery observations
Q adds presentation and derived read models to the existing monolith, not a second task manager or execution path. `lib/operating-views.ts` projects public facts; `dashboard/src/server/operating-view-service.ts` supplies contained, validated, no-migration snapshots. Four closed, validated, no-store GETs expose derived API v1: `/api/operating/overview`, `/api/operating/objectives/:id`, `/api/operating/projects/:id` and `/api/operating/issues/:id`. Their version is independent of persisted document versions. Invalid identifiers, unknown/duplicate query fields and invalid cursors are refused; missing focus is distinguished from unavailable source coverage.
The eleven sections carry availability (`available`, `absent`, `unavailable` or `not-enabled`), reason, origin, saved observation time, freshness and coverage. Readers share aggregates only within one request and isolate independent failures. Missing optional stores are not malformed stores; invalid/future records, unsafe paths and unreadable task collections are not filtered into invented empty inventories. The service caps general snapshots/task collection bytes at 16 MiB, selected portfolio/Harness/session snapshots at 10 MiB, and normalized source facts at 10000; tighter existing store limits still apply. These are bounded cooperating-writer snapshots, not an atomic cross-store read or protection against arbitrary same-user filesystem races.
Requested `page_size` is 1..50; each response section/page may contain zero to 50 rows, ordered by ID, not by criticality, due date or recency. Cursors bind view/focus/section/source observation, not an immutable global snapshot. Exact totals require complete validated joined coverage; otherwise totals remain null and `has_more` may be unknown. Date-only review facts remain dates, never midnight observation timestamps. Saved facts do not acquire fresh evidence merely because a request is new. The default operating signal section has no saved-feed adapter and remains unavailable: Q GETs do not call the live signal service, provider refresh, Harness inspection, migration, reconciliation, budget admission or runtime.
SURTEC/objective detail, Today lineage, project readiness and issue/task panels reuse the existing views and protected actions. Canonical ancestry and same-project links remain explicit; an issue without an objective does not inherit every objective linked to its project. Personal/experimental work needs no fabricated client, objective or Harness installation. Six primary issue labels are presentation only; proposed/authorized/cancelled remain distinct, a finished task is not an accepted issue, and unknown current Git/candidate validity is not success. Navigation and generic private-safe task prefills grant no execution authority or implicit context consent. Editor launch remains explicitly separate from in-app project detail. Harness remediation is inert preview; recorded validation is distinct from file presence or a matching hash.
`DeliveryReadinessPanel` consults exact issue lineage explicitly in issue, project and saved-commitment contexts. Technical acceptance, reviewed readiness, environment observation, handoff, client response and follow-up are independent facts. Builds, healthy URLs, completed tasks/commitments and operator text cannot imply another fact, verified delivery or client acceptance. Private manual summary/source/next action are revealed per record as text, not copied to overview, Today, generic prefills or implicit model context.
The only new write is `POST /api/work-issues/:id/delivery-observations`: an 8-KiB, no-store, loopback/origin/session-protected append through the existing issue writer. It requires explicit confirmation and exact current project/issue revision/scope plus an all-null or exact latest non-invalidated candidate binding. Optional commitment references must already be linked to that issue and resolve to the same project through a bounded stable read, not a commitment mutation or cross-store transaction. Queued/running task ownership, nonterminal workflow ownership, unavailable ownership, stale requests and capacity overflow refuse recording. The strict optional nested `delivery_observation` v1 facet records one of five operator-entered kinds with separate observed/server-recorded times, bounded private fields and inert source references; it is informational evidence with no task/run identity or testing receipt. At most 64 manual records per issue fit within existing aggregate limits, without eviction.
Issue lifecycle, authorized scope, task/grant ownership, correction caps, commitments, publication and runtime are unchanged. Historical absent facets stay absent; malformed/null/future facets fail closed without repair or backfill. See the [Q compatibility addendum](organization-state-migration.md#phase-q-read-model-and-delivery-facet-compatibility), [Q design](phase-q-operating-views-design.md) and [Q acceptance record](../runbooks/phase-q-acceptance.md) for actual verification status. Scoped implementation is not evidence that the final whole-repository gate passed. P remains a partial T001-T014 delivery with T015-T026 deferred; Q does not activate production budget cutover, routine effects or continuity operations. Its budget section remains `not-enabled` and continuity `deferred`.
