## Finite templates

Templates are code-owned, sequential and versioned. A server validates role-to-existing-agent mappings; an unavailable role blocks selection rather than choosing a substitute. One non-terminal workflow may own an issue at a time. Independent existing tasks still obey global scheduler capacity and one project writer.

| Template | Allowed sequence | Human boundary / issue behavior |
| --- | --- | --- |
| analysis | PortfolioAnalyst **or** Planner, then review | Root approval and final human acknowledgement; analysis never authorizes or completes its linked issue |
| implementation | Planner, approved plan, SoftwareEngineer, trusted verification, Reviewer, QA when required, decision | Root approval, exact-plan/write approval, final candidate acceptance; optional one bounded correction loop |
| quality-review | Reviewer, QAEvaluator, decision over an existing current candidate | Root/candidate approval and final decision; no automated correction or backward issue transition |
| operations-investigation | OperationsObserver, structured proposed issue or next action, decision | Root approval and human acknowledgement of proposal; no automatic issue creation, execution or publication |
| trivial-change | Authorized SoftwareEngineer, applicable verification, required review/QA, decision | Only classified trivial work; omit Planner, not current review/testing floors or human issue acceptance |

Every issue transition goes through the existing v1 guard, policy, actor, revision and evidence checks. Workflow transitions describe orchestration, not a replacement lifecycle. A model's completion claim, recommended next action or requested decision cannot advance either state machine by itself.

Workflow statuses are `running`, `waiting-human`, `needs-decision`, `completed` and `cancelled`. Preview is ephemeral, not a persisted draft. Stage statuses are `pending`, `reserved`, `queued`, `running`, `completed`, `needs-review`, `failed` and `cancelled`; recovery separately reports `none`, `reconciling` or `awaiting-human`. Templates constrain the next stage; only current human decisions or infrastructure-validated facts may advance it. Completed/cancelled workflow authority is terminal. Replacement creates a new grant/generation with retained lineage, never reopens terminal authority. A role's requested decision pauses chaining even when its normal successor was enumerated.

## Review policy and immutable evidence

Intrinsic review depth is passive for trivial non-behavioral documentation, focused for bounded behavior changes, and full for security/authentication/authorization, persistence/migrations, payments, infrastructure, critical client operations or broad cross-domain changes. Effective depth is the maximum of this result and all current trusted floors. Current defaults therefore never execute passive-only acceptance. Show both intrinsic/effective depth and exact reasons. Full depth and any explicit trusted QA requirement mandate QA; quality-review always includes it.

Workflow-managed implementation records the existing candidate and independently captured testing receipt but stays checking after verification passes. The controller may record review handoffs only after the owning implementation task has finished with valid structured output, its lease is inactive and the exact candidate/receipt binding passes. Partial, failed or ambiguous output does not silently become review success. Verification failure or missing strict-TDD observations remains visible needs-decision; a Reviewer cannot waive it.

Reviewer and QA inspect the **candidate's managed worktree**, never assume the project checkout contains its changes. Resolve its owner from authoritative task/run metadata, reject caller-supplied paths and confirm canonical containment, repository identity, base and candidate commit, clean tree/index and changed-path/content fingerprint before and after the read-only turn. No verification capability is added to these read-only roles: QA evaluates the controller-captured receipt and criteria. Unexpected mutation invalidates review and stops progression. Different roles use separate task/thread contracts; implementer thread history is never reused by review.

Keep ReviewCandidate v1 unchanged. A new ReviewReceipt v1 binds workflow/stage/task/run, logical role and adapter, issue/scope revision, candidate id/base/commit/paths/diff fingerprint, testing receipt fingerprint, context and review-policy fingerprints, grant authority revision, verdict/findings, timestamp and its own fingerprint. Infrastructure creates the binding and validates referenced evidence; role output supplies bounded observations/recommendations, not verification truth or delivery permission. Receipts are immutable. New candidate, scope, relevant policy or authority changes invalidate applicability rather than editing a receipt.

For quality-review of an already ready-for-review candidate, preserve its issue status and require current bound reviews before acceptance. Do not manufacture ready-for-review to checking. A missing legacy testing binding blocks this new workflow and requires explicit governed rework; non-workflow historical acceptance behavior is not retroactively rewritten.

Advisory known-risk acknowledgement is a candidate-and-receipt-bound human decision. It never waives failed/missing trusted checks, changed protected probes, scope violations or stale review. A stale candidate is rejected even after clicking an acknowledgement. Human needs-decision resolution retains its existing invalidation semantics; it does not revive the invalidated candidate.

## Single correction and budgets

Correction is opt-in and off by default. A server-created immutable candidate-lineage identity ties the initial implementation task and its candidates, descendant correction candidate and any workflow replacement. The aggregate retains a consumed allowance even after cancellation or replacement. No retry, new record id or repeated candidate review resets it. A separate human-approved new work cycle is not an automatic retry.

Eligibility requires checking, a current passed-verification candidate, concrete in-scope findings, an unchanged approved grant and the original authorized engineer. Reserve/consume the allowance before queuing. Never change protected Harness/policy/approval sources or trusted verification probes. Start a new owned correction worktree from the exact prior candidate commit, not the source checkout HEAD; use a new task/thread. Existing scope/protected-path guards remain authoritative. Capture fresh trusted verification and a new candidate fingerprint, then rerun required Reviewer/QA stages. Failed/inconclusive correction, remaining findings or exhausted budget stops at needs-decision. A ready-for-review candidate needs human rework, not this automatic edge.

Workflow policy v1 contains only reviewed finite controls; no roles, commands or graphs can be added through it. Default root caps: 7 model tasks, 10 attempts, 900000 ms of accumulated active runtime and 100000 total tokens. Hard ceilings: 7 tasks, 14 attempts, 1800000 ms and 300000 tokens. The longest opt-in implementation path fits seven stages: Planner, Engineer, Reviewer, QA, corrected Engineer, Reviewer, QA. Verification is infrastructure, not an extra model task. Templates needing fewer stages do not automatically consume extra slots.

Opt-in correction subcaps are at most 3 tasks, 4 attempts, 300000 ms and 40000 tokens, all drawn from remaining root authority; they are not extra capacity. Display remaining caps before approval. Stage budgets intersect role defaults, project/worker constraints and root remainder. Consumed runtime includes verification in the active attempt. Deduplicate monotonic token observations by execution id; charge attempts before execution. Budget cancellation is wired to the running task. Unknown usage after interruption is a visible decision, not zero usage. Tokens may overshoot a cap by an in-flight reported chunk; abort immediately and never admit another stage. No monetary-cost estimate or guaranteed provider billing limit is claimed.

## Durable state and recovery protocol

Use `state/workflows/workflows.json` with WorkflowDocument v1: records, bounded stages, grants/decisions, handoffs, review receipts, admission intents, usage accounting, correction-lineage allowances and operational events. Code ceilings: 500 workflows, 10000 total stage generations, 5000 handoffs, 5000 review receipts, 20000 events and 16 MiB aggregate. Reject further mutation at a limit without pruning evidence or rewriting an old document. Nested records have bounded strings/arrays and strict schema validation. Validate workflow/project/issue/owner links and at most one non-terminal issue owner.

Reuse existing named locks and unique temporary atomic replacement. Workflow, issue and task files are **not** one transaction. No workflow lock is held while acquiring an issue/task/scheduler lock; controller phases reread and compare revisions. Before execution, scheduler integration rechecks a committed workflow intent and exact authority outside conflicting nested-lock order, then validates its claim token/lease. An unavailable required aggregate blocks execution rather than treating the task as ordinary legacy work.

1. Reserve stable stage/generation/task identities and a bounded admission intent under the workflow lock; release it.
2. Revalidate policy and current issue, create the exact reserved task id through an internal trusted workflow boundary and record existing issue linkage as appropriate. Do not enqueue arbitrary public metadata.
3. Reconcile durable task/issue facts into a committed intent. The scheduler cannot start an uncommitted intent. Repeated reconciliation uses the same task id.
4. Observe terminal snapshots/receipts using the current run id and lease fence; seal output/handoff once. Duplicate callbacks/ticks cannot create another downstream task or charge usage twice.
5. Recompute the next allowed transition from durable facts, current scope/candidate, grant and budgets. Proven incomplete intents may be finalized idempotently; unprovable gaps pause for a human. Never redispatch simply because a callback was lost.

Use the existing TaskOrchestrator to claim, lease, limit capacity, run, abort and retry tasks. Add a small WorkflowOrchestrator/controller for finite transition/reconciliation hooks, not another execution scheduler, worker loop or provider. Bootstrap it once for server and inject the same controller in fixtures. Historical tasks take their unchanged path; v2 workflow tasks cannot be executed by standalone CLI/run-task without valid controller authority.

Transient same-stage retry reuses the reserved identity only with unchanged contract and available aggregate/per-task budget. Expired lease recovery fences old callbacks; an already frozen candidate is recovered for review rather than another write. Replacing a stage requires a current human decision, fixed role/scope, new generation and retained lineage/counters; owner reassignment remains unsupported. Replacing a whole workflow first terminates its old authority and carries the applicable correction allowance. Root cancellation durably prevents downstream admission, requests task abort, then retains receipts/handoffs and a next action. It does not silently cancel the linked issue or delete candidate worktrees.

Manual issue dispatch/rework, task retry, CLI mutations, publication and task reject/cleanup must consult active workflow authority. The human can stop the workflow and use the existing independently authorized actions afterward; workflow acceptance itself never triggers push/PR/merge/deploy. A cleanup cannot remove a tree still required by an active review.
